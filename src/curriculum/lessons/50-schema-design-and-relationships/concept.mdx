# Schema Design and Relationships

An online shop started with one table, because one table was enough. Each invoice row carries the customer's name and email right next to the amount, so the receipt screen never needs a join.

```sql
CREATE TABLE invoices_flat (
  id serial PRIMARY KEY,
  customer_name text,
  customer_email text,
  total int
);
```

Ada has two invoices and Grace has one. Then Ada changes her email address, and the settings screen runs the update the obvious way: find Ada's row and change it.

```sql
UPDATE invoices_flat SET customer_email = 'ada@newmail.com' WHERE id = 2;
SELECT id, customer_name, customer_email FROM invoices_flat ORDER BY id;
```

Ada now has two email addresses, depending on which invoice you ask. The update was not wrong; it changed the row it was told to. The schema is wrong, because a fact about Ada, her email, is stored once per invoice instead of once per Ada, and nothing in the database knows those copies are supposed to agree. The receipt for invoice 1 will go to an address she no longer reads. This lesson is about deciding where each fact lives, how tables point at each other, and which rules the database itself should enforce so that this class of bug cannot be written.

## Each fact lives in one place

The fix is to notice that the flat table describes two kinds of thing. An invoice has a total. A customer has a name and an email. They are different **entities**, and the first rule of schema design is one table per entity, with each fact stored exactly once. The invoice then refers to its customer by id rather than carrying a copy of the customer. The rebuilt schema below calls the invoice table `orders`, the shop's own word for the same record, and gives it the columns the flat table was missing.

```sql
CREATE TABLE customers (
  id serial PRIMARY KEY,
  name text NOT NULL,
  email text NOT NULL UNIQUE
);

CREATE TABLE orders (
  id serial PRIMARY KEY,
  customer_id int NOT NULL REFERENCES customers(id) ON DELETE RESTRICT,
  total_cents int NOT NULL CHECK (total_cents >= 0),
  status text NOT NULL DEFAULT 'draft'
);
```

Two pieces of vocabulary carry the design. A **primary key** is the column that identifies one row, here `id`, generated by the database with `serial` so no two rows share it. A **foreign key** is a column in one table that holds the primary key of a row in another, and `REFERENCES customers(id)` tells the database that `orders.customer_id` must always name a real customer. The relationship is **one-to-many**: one customer, many orders, expressed entirely by the many side pointing at the one side. With the email stored once, the settings screen updates one row and every order sees the change.

```sql
UPDATE customers SET email = 'ada@newmail.com' WHERE id = 1;
SELECT o.id, c.name, c.email FROM orders o JOIN customers c ON c.id = o.customer_id ORDER BY o.id;
```

Splitting facts into their own tables this way is called **normalization**. The price is the join: the receipt screen now reads two tables instead of one. Lesson 49 showed that joins are cheap to write and lesson 51 shows how to keep them cheap to run. The anomaly they prevent is not cheap at all.

## Constraints are rules the database enforces

The `orders` table above carries four rules that the flat table did not, and each one turns a category of application bug into an immediate, loud error. The foreign key rejects an order for a customer who does not exist:

`NOT NULL` says a column must have a value in every row. `UNIQUE` says no two rows may share a value, which is how the schema promises that an email identifies one customer. `CHECK` states a rule about a single row, here that a total is never negative. Each of these could be enforced in application code instead, and lesson 46's pipeline validates requests before they reach the handler for exactly that reason. The difference is that there is one database and many code paths: an import script, an admin tool, a migration, a second service. A constraint in the schema holds for all of them, including the ones nobody has written yet.

Nullability deserves a decision per column rather than a default. Lesson 49's `status` column allowed `NULL`, and the report that filtered on it silently dropped rows. In the new schema `status` is `NOT NULL DEFAULT 'draft'`: an order always has a status, and a caller who does not name one gets the sensible starting value. The question to ask of every column is whether "unknown" is a real state of the world for it. A shipping date is legitimately unknown until the order ships, so it should be nullable. A status is never unknown, so it should not be.

## Many-to-many needs a third table

Some relationships do not fit one-to-many. An order can carry several tags, and a tag applies to many orders. The tempting shortcut is a text column holding `'rush,gift'`, and it fails the moment anyone asks for all rush orders, because the only query is a substring match that also finds `'rushed'` and cannot use an index. The relational answer is a **join table**, one row per pairing:

```sql
CREATE TABLE tags (id serial PRIMARY KEY, name text NOT NULL UNIQUE);

CREATE TABLE order_tags (
  order_id int NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  tag_id int NOT NULL REFERENCES tags(id),
  PRIMARY KEY (order_id, tag_id)
);
```

The **composite primary key** on the pair does two jobs: it identifies each row, and it makes tagging the same order with the same tag twice impossible. Finding rush orders is then an ordinary pair of joins.

## Deleting a parent is a design decision

Once tables point at each other, deleting a row that other rows point at has to mean something, and the foreign key's `ON DELETE` clause is where that meaning is written. There are three useful answers. **`RESTRICT`** refuses the delete while children exist. **`CASCADE`** deletes the children too. **`SET NULL`** keeps the children and blanks their reference. The new schema uses all three, and each was chosen for a reason. The third appears on a table not shown yet, a log of reminder emails sent about an order:

```sql
CREATE TABLE reminders (
  id serial PRIMARY KEY,
  order_id int REFERENCES orders(id) ON DELETE SET NULL,
  sent_at date NOT NULL
);
```

Read the three choices as statements about the business. Orders are financial records, so a customer with orders cannot simply vanish: `RESTRICT`, and the application must decide what to do about the orders first. A tag pairing has no meaning without its order, so it goes when the order goes: `CASCADE`. A reminder is a record that an email was sent on a date, which stays true after the order is gone, so it survives with its reference blanked: `SET NULL`, which also means `reminders.order_id` must be nullable, a nullability decision forced by the delete decision. `CASCADE` is the one to be careful with, because cascades chain: deleting a customer whose orders cascade whose tags cascade removes three tables' worth of rows in one statement. The second practice problem has you compute exactly what one delete would do given a set of foreign keys, including the case where a `RESTRICT` two levels down blocks the whole thing.

## When copying a value is right

Normalization says store each fact once, and the opener shows why. But some values that look like copies are facts about a different entity. An order line stores the price the customer paid, and it must keep storing that price after the product's price changes, because the fact being recorded is "what this order cost," not "what this product costs." That is a **snapshot**, and it is correct to copy. The test is whether the value should change when the source changes. Ada's email on an invoice should follow Ada, so it must not be copied. The price on a line should stay put when the catalog moves, so it must be.

Deliberate copying for speed, called **denormalization**, is a separate thing: keeping a `member_count` on a club row so the club list does not run a count per club. It buys a faster read at the price of a write that must update two places and can drift, which is the opener's bug reintroduced on purpose. The rule is to normalize first, measure, and denormalize only the specific read that is too slow, with the code that keeps the copy in sync written next to the copy.

## Common mistakes

These are the schema errors that show up most often in growing applications and in design interviews:

- Storing a fact about one entity on the rows of another, like a customer's email on every invoice, so an update fixes one copy and leaves the rest stale.
- Leaving out foreign keys because the application "always" inserts valid ids, until an import script or a second service does not.
- Storing a list in one column as comma-separated text, which cannot be searched exactly, indexed, or constrained.
- Modeling a many-to-many relationship without a join table, or with a join table that lacks a primary key on the pair, so duplicates creep in.
- Letting every column be nullable by default instead of deciding, per column, whether "unknown" is a real state.
- Choosing `ON DELETE CASCADE` for convenience on financial or audit records, so one delete silently removes history.
- Choosing `RESTRICT` everywhere and then deleting children by hand in application code, reinventing cascade without the guarantee.
- Denormalizing before measuring, and reintroducing the update anomaly to speed up a query that was never slow.
