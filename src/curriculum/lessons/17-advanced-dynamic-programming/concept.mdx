# Advanced Dynamic Programming

In the last lesson, every state was identified by a single number. "The number of routes to step 3" needed only the step number. "The fewest coins that form amount 6" needed only the amount. One number was enough to say exactly which smaller problem you meant.

Some problems refuse to fit in one number. Picture a grid of city blocks where you can only walk right or down, and you want the cheapest route from the top-left corner to the bottom-right. Try to define a state with one number, say "the cheapest route to column 2." Cheapest route to column 2 of which row? The cost of reaching column 2 in the top row and the cost of reaching column 2 in the bottom row are different answers to different questions. To name one subproblem you need two numbers, a row and a column, so the state becomes a cell in a two-dimensional table instead of an entry in a list.

<AdvancedDynamicProgrammingDiagram />

That is the whole jump this lesson makes. States, base cases, and transitions work exactly as before; there are just more coordinates in each state's name. The discipline that matters is adding a coordinate only when it changes the answer on its own. Row changes the cheapest cost even when column stays fixed, and column changes it even when row stays fixed, so the grid problem genuinely needs both. If two candidate coordinates always move together, or one is computable from the other, you are paying for table space that buys nothing. As in the last lesson, write the one-sentence meaning of a state first, and let that sentence tell you how many coordinates the table needs.

## Read neighboring grid states

Here is the grid problem as an interview would phrase it: move only right or down through a grid of nonnegative numbers, and return the minimum sum of the numbers along a path from the top-left cell to the bottom-right cell.

Let the state at `(row, column)` be the minimum sum of a path ending at that cell. Since every move goes right or down, the final step into any cell came from the cell above it or the cell to its left, so the transition takes the smaller of those two neighbors and adds the current cell's value. The base case is the top-left cell, which costs only its own value because no travel is needed to start there.

Take `grid = [[1, 3, 1], [1, 5, 1], [4, 2, 1]]`. Filling the full two-dimensional table row by row, each cell holding the cheapest sum to reach it, gives:

```
grid          cheapest sums
1  3  1       1  4  5
1  5  1       2  7  6
4  2  1       6  8  7
```

Check one entry by hand. The middle cell holds 7 because its neighbors above and to the left hold 4 and 2, and the cell's own value 5 plus the smaller neighbor gives 2 + 5 = 7. The bottom-right corner holds 7, which is the answer.

Now look at what each row of that table needed. Row 1 was built entirely from row 0 and from row 1's own earlier entries. Row 0 was never touched again after that. This is the same observation that let the staircase code keep two variables instead of a whole list, and it invites the same space compression: keep one array the width of the grid and overwrite it row by row.

```ts
export function minimumGridPathSum(grid: number[][]): number {
  const columnCount = grid[0].length
  const minimumSums = Array<number>(columnCount).fill(Infinity)
  minimumSums[0] = 0

  for (let row = 0; row < grid.length; row += 1) {
    for (let column = 0; column < columnCount; column += 1) {
      // Not overwritten yet, so this is still the cell above:
      // the previous row's value at this same column.
      const fromAbove = minimumSums[column]
      // Already overwritten this pass, so this is the current
      // row's value one cell to the left.
      const fromLeft = column > 0 ? minimumSums[column - 1] : Infinity

      minimumSums[column] = grid[row][column] + Math.min(fromAbove, fromLeft)
    }
  }

  return minimumSums[columnCount - 1]
}
```

`minimumGridPathSum([[1, 3, 1], [1, 5, 1], [4, 2, 1]])` returns `7`, matching the table.

The compression works because of when each entry gets overwritten. Before the loop reaches an entry, that entry still holds the row above's value. The moment the loop passes it, it holds the current row's value. Both reads in the loop rely on this timing: `minimumSums[column]` has not been overwritten yet, so it is the cell above, while `minimumSums[column - 1]` was overwritten one step ago, so it is the current row's left neighbor.

Watch it happen on row 1 of the example. Entering the row, the array holds row 0's results, `[1, 4, 5]`. At column 0 there is no left neighbor, so the new value is the cell above plus the grid value, 1 + 1 = 2, and the array becomes `[2, 4, 5]`. At column 1, `minimumSums[1]` still holds 4, which is row 0's entry, the cell above. `minimumSums[0]` was just overwritten to 2, which is row 1's entry, the cell to the left. The new value is 5 + min(4, 2) = 7, and the array becomes `[2, 7, 5]`. At column 2, the untouched 5 is the cell above and the fresh 7 is the cell to the left, giving 1 + min(5, 7) = 6. The array ends the row as `[2, 7, 6]`, exactly row 1 of the full table. One array played both rows, above and current, at once.

## Use one position from each string

Grids are not the only source of two-coordinate states. Comparing two strings needs one too, because a subproblem must say how far into each string it has looked.

The classic prompt: given two strings, return the length of their longest common subsequence. A subsequence keeps characters in order but may skip over others, so `"ace"` is a subsequence of `"abcde"`. That makes it different from a substring, which must be contiguous; `"ace"` is not a substring of `"abcde"` because `b` and `d` sit in the way. Interviews mix these two words up on purpose, so read the prompt carefully.

The states here are built from prefixes. A prefix of a string is simply its first however-many characters; the prefixes of `"ace"` are the empty string, `"a"`, `"ac"`, and `"ace"`. Let `lengths[i][j]` be the longest common subsequence length between the first `i` characters of `left` and the first `j` characters of `right`. One coordinate per string, because how far you have read in `left` and how far you have read in `right` change the answer independently.

With `left = "abcde"` and `right = "ace"`, the full table looks like this, with each row labeled by a prefix of `left` and each column by a prefix of `right`:

```
           ""   "a"  "ac" "ace"
    ""      0    0    0    0
    "a"     0    1    1    1
    "ab"    0    1    1    1
    "abc"   0    1    2    2
    "abcd"  0    1    2    2
    "abcde" 0    1    2    3
```

The transition has three cases, and it helps to say each one in plain words before reading the code. The base case is any comparison against an empty prefix: nothing shared with nothing is length 0, which fills the first row and first column. When the final characters of the two prefixes match, that shared character extends whatever the two prefixes without it had in common, so the answer is one more than the diagonal neighbor up and to the left. When they do not match, the final character of at least one prefix is dead weight; drop it from `left` or drop it from `right`, and keep the better of those two already-solved answers.

```ts
export function longestCommonSubsequenceLength(
  left: string,
  right: string,
): number {
  const lengths = Array.from({ length: left.length + 1 }, () =>
    Array<number>(right.length + 1).fill(0),
  )

  for (let leftLength = 1; leftLength <= left.length; leftLength += 1) {
    for (let rightLength = 1; rightLength <= right.length; rightLength += 1) {
      if (left[leftLength - 1] === right[rightLength - 1]) {
        // Final characters match: extend the answer for both
        // prefixes without them, the diagonal cell up-left.
        lengths[leftLength][rightLength] =
          lengths[leftLength - 1][rightLength - 1] + 1
      } else {
        // No match: drop the final character of one prefix or the
        // other (cell above vs cell to the left) and keep the better.
        lengths[leftLength][rightLength] = Math.max(
          lengths[leftLength - 1][rightLength],
          lengths[leftLength][rightLength - 1],
        )
      }
    }
  }

  return lengths[left.length][right.length]
}
```

`longestCommonSubsequenceLength("abcde", "ace")` returns `3`, the bottom-right cell of the table.

This code keeps the full table rather than compressing it, and that is a fine place to stop. Each cell reads its up, left, and up-left neighbors, so a rolling one-row version is possible with care, but the last lesson's advice still stands: compress only after the full-table version is correct, and only when the memory actually matters. Keeping the table also pays off if the prompt asks for the subsequence itself rather than its length, because the choices can be walked backward through the stored cells.

## Preserve one-use choices during compression

The last problem shows why compression is a correctness question, not just a memory trick. You are given items, each with a weight and a value, a weight capacity, and one rule: each item may be taken at most once. Maximize the total value without exceeding the capacity.

The state needs two coordinates again: which items have been considered, and how much capacity is being used. Let the full table's cell at `(item, remainingCapacity)` be the best value using only the first `item` items within that capacity. Each item is either skipped, keeping the value from the row above at the same capacity, or taken, adding its value to the row above's entry at the reduced capacity. Reading from the row above is what enforces the one-use rule: the smaller subproblem was solved before this item existed, so it cannot possibly contain it.

With `capacity = 5`, `weights = [1, 2, 3]`, and `values = [6, 10, 12]`, the full table fills row by row, one row per "items considered so far":

```
capacity:          0   1   2   3   4   5
no items           0   0   0   0   0   0
+ item 1 (w1 v6)   0   6   6   6   6   6
+ item 2 (w2 v10)  0   6  10  16  16  16
+ item 3 (w3 v12)  0   6  10  16  18  22
```

The bottom-right cell, 22, comes from taking items 2 and 3 for weight 5 and value 10 + 12. Each row only ever reads the row above, so the same compression as the grid applies: one array, overwritten once per item. But this time the loop must run in a specific direction, and getting it wrong quietly changes the answer.

```ts
export function maximumKnapsackValue(
  capacity: number,
  weights: number[],
  values: number[],
): number {
  const bestValues = Array<number>(capacity + 1).fill(0)

  for (let item = 0; item < weights.length; item += 1) {
    const weight = weights[item]
    const value = values[item]

    // Walk capacity from high to low so every read below lands on
    // a value from the previous item's row, never one this item wrote.
    for (let currentCapacity = capacity; currentCapacity >= weight; currentCapacity -= 1) {
      bestValues[currentCapacity] = Math.max(
        // Skip this item: the row above at the same capacity.
        bestValues[currentCapacity],
        // Take this item: the row above at the reduced capacity,
        // still unwritten this pass because the loop is descending.
        bestValues[currentCapacity - weight] + value,
      )
    }
  }

  return bestValues[capacity]
}
```

`maximumKnapsackValue(5, [1, 2, 3], [6, 10, 12])` returns `22`, matching the table.

Why must the capacity loop descend? This is the subtlest point in the lesson, so trace both directions on just the first item, weight 1 and value 6, starting from the all-zero array.

Suppose the loop ran ascending instead. At capacity 1, the take option reads `bestValues[0]`, which is 0, so the entry becomes 6. So far so good. At capacity 2, the take option reads `bestValues[1]`. But the loop already overwrote that entry this same pass, so it reads 6, not the previous row's 0, and the entry becomes 12. That 6 already contains this item, and adding the item's value on top of it takes the item a second time. The error compounds: capacity 3 becomes 18, and capacity 5 ends at 30, as if five copies of a take-it-once item were allowed. The full table's row for item 1 says every capacity should hold 6.

Now run it descending, as the code does. At capacity 5, the take option reads `bestValues[4]`, an entry the loop has not reached yet, so it still holds the previous row's 0, and the entry becomes 6. Same at capacities 4, 3, 2, and 1: every read lands below the loop's current position, in territory not yet overwritten, so every read sees the row above. The array ends the pass as `[0, 6, 6, 6, 6, 6]`, exactly the full table's row.

The grid problem wanted one read from the current row and updated ascending; this problem must never read the current row and so updates descending. Same one-array trick, opposite directions, and the full table is what tells you which one is right. That is why the update direction is part of the algorithm's correctness here, not a style choice.

## Common mistakes

These are the errors that show up most often when states grow a second dimension:

- Adding a dimension without being able to say, in one sentence, what each coordinate of a state means.
- Adding a dimension that does not change the answer on its own, which multiplies table size for nothing.
- Filling the table in an order that reads a cell before it has been computed, such as visiting grid cells column-first when the transition reads from the left.
- Solving for a substring when the prompt says subsequence, or the reverse; the first must be contiguous, the second only in order, and the algorithms differ.
- Omitting the empty-prefix row and column in a string table, which removes the base cases every other cell is built on.
- Updating one-use knapsack capacity ascending, which lets the current pass read its own writes and count an item twice, as traced above.
- Compressing a table without checking which old values each transition still needs; the grid and knapsack loops run in opposite directions for exactly this reason.
- Returning only the optimal value when the prompt also asks for the path or the chosen items, which requires keeping enough of the table to walk the choices backward.
- Reporting complexity from table dimensions alone while forgetting the work done inside each transition.
