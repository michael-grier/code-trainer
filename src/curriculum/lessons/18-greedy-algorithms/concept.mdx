# Greedy Algorithms

A greedy algorithm makes one preferred choice at a time and does not reconsider earlier choices. This is safe only when that choice cannot remove a better complete answer. The rule needs a correctness argument, not only examples where it works.

<GreedyAlgorithmDiagram />

The most common argument is an exchange: take some best-possible answer, swap one of its choices for the greedy choice, and check that the answer did not get worse. Here is what that looks like on a real instance. Suppose you are scheduling meetings from the list `[[1, 3], [2, 4], [3, 5], [0, 7], [5, 7]]`, where each pair is a start and end time, and you want to attend as many as possible. Imagine someone hands you a best-possible schedule that starts with `[2, 4]`. The meeting that ends earliest in the whole list is `[1, 3]`. Swap it in as the new first meeting. Every later meeting in that schedule started at time 4 or after, and `[1, 3]` ends at 3, before the meeting it replaced ended, so every later meeting still fits. The swapped schedule has the same number of meetings, which means the greedy first choice belongs to some best-possible answer too. Repeating that swap down the schedule is the proof, and this lesson leans on that style of argument in each example.

## Keep only the farthest reachable boundary

The first problem: each array value gives the maximum forward jump allowed from its index, and the question is whether the final index is reachable.

Take the input `maximumJumps = [2, 3, 1, 1, 4]` and start tracking one number, the farthest index any jump sequence has reached so far. Standing at index 0, you may jump forward 1 or 2 positions, so indexes 1 and 2 are reachable and the boundary is 2. Index 1 sits inside that boundary, and from it you may jump up to 3 forward, landing as far as index 4. The boundary becomes 4, which is the last index, so the answer is `true`.

Notice what got thrown away in that trace. Index 2 is reachable two different ways, directly from 0 or through 1, and the trace never recorded which. It does not need to, because a jump of length up to `k` lets you land on any of the next `k` indexes, not only the farthest one. So if the boundary is 4, you can stop at 1, 2, 3, or 4 as you please; every index at or before the boundary is reachable by some route. How you got there changes nothing about where you can go next. That is the greedy compression: replace all routes with the single number they collectively reach.

```ts
export function canReachLastIndex(maximumJumps: number[]): boolean {
  let farthestReachable = 0

  // Only visit indexes the boundary has already proven reachable.
  for (let index = 0; index <= farthestReachable; index += 1) {
    // A jump from here may extend how far any route can reach.
    farthestReachable = Math.max(
      farthestReachable,
      index + maximumJumps[index],
    )

    if (farthestReachable >= maximumJumps.length - 1) {
      return true
    }
  }

  return false
}
```

`canReachLastIndex([2, 3, 1, 1, 4])` returns `true`.

The loop stops when `index` moves beyond the reachable boundary, which means progress has stalled: no visited index can push the boundary any further. A zero inside the boundary is harmless if an earlier index already reaches beyond it, because routes are free to hop over it.

## Leave the most room for later intervals

The second problem is the meeting scheduling question from the introduction: how many meetings can one person attend without overlap? Meetings here are half-open, meaning a meeting that ends at time 3 does not collide with one that starts at time 3.

Sort meetings by end time and select the next compatible meeting that ends earliest. This is the swap argument from the introduction applied at every step: replacing a later-ending choice with the earliest-ending compatible meeting cannot reduce the time available afterward.

Here it is on the introduction's list, `meetings = [[1, 3], [2, 4], [3, 5], [0, 7], [5, 7]]`:

```ts
type Meeting = [start: number, end: number]

export function maximumNonOverlappingMeetings(meetings: Meeting[]): number {
  // Sort a copy by end time so the earliest-ending option always comes first.
  const sorted = meetings
    .map(([start, end]): Meeting => [start, end])
    .sort((left, right) => left[1] - right[1] || left[0] - right[0])

  let selectedCount = 0
  let previousEnd = Number.NEGATIVE_INFINITY

  for (const [start, end] of sorted) {
    // Half-open meetings may share an endpoint, so >= means compatible.
    if (start >= previousEnd) {
      selectedCount += 1
      previousEnd = end
    }
  }

  return selectedCount
}
```

The function returns `3`, selecting `[1, 3]`, `[3, 5]`, and `[5, 7]`.

Sorting by start time does not provide the same guarantee. An early-starting meeting may occupy most of the schedule and block several shorter meetings.

## Delay a choice until it becomes necessary

The last problem sends a truck toward a target position with some starting fuel, past stations that each offer a known amount of fuel. Return the fewest refueling stops that get it there, or `-1` if the target is unreachable.

The two examples above committed to each choice the moment it appeared. This problem rewards the opposite habit: postpone every choice until the moment one is forced.

Here is the trick on a concrete trip. Take `target = 100`, `startFuel = 10`, and `stations = [[10, 60], [20, 30], [30, 30], [60, 40]]`, where each pair is a station's position and the fuel it offers. The truck starts with 10 units of fuel, so it can reach position 10. It rolls past the station there, which offers 60 units, and writes that offer down without stopping. At position 10 the tank is dry and the target is far away, so a stop is now unavoidable. Which stop? The truck decides retroactively: of all the stations it has passed, count a stop at the one with the most fuel. That is the station at position 10 with 60 units, so the reachable range grows to 70. Rolling on, it passes the stations at 20, 30, and 60, writing down 30, 30, and 40. At position 70 it is dry again, still short of 100, so it counts a second retroactive stop at the best passed station, the one offering 40, and the range grows to 110. That covers the target, so the answer is `2`.

The step that deserves suspicion is "count a stop retroactively." Why is the truck allowed to claim, at position 70, that it stopped back at position 60? Because every station it wrote down was within reach when the truck passed it, so a real trip could have included that stop. Driving past a station never forfeits it as an option. Delaying the commitment simply lets the truck wait until it knows which passed station turns out to be the most valuable, instead of guessing at the moment it drives by. The greedy rule, take the largest recorded fuel amount each time a stop is forced, has the usual exchange argument behind it: swapping any counted stop for a larger passed offer only increases range and can never increase the stop count.

The code needs one supporting structure. A max-heap is a container that hands back the largest stored value quickly, which is exactly the "best passed station" lookup the truck performs each time it runs dry. JavaScript has no built-in heap, so this example carries small `pushMax` and `popMax` helpers, shown after the main function.

```ts
export function minimumRefuelStops(
  target: number,
  startFuel: number,
  stations: Array<[position: number, fuel: number]>,
): number {
  // Fuel offers from every station passed so far, largest on top.
  const availableFuel: number[] = []
  let reachablePosition = startFuel
  let stationIndex = 0
  let stopCount = 0

  while (reachablePosition < target) {
    // Record the offer from every station inside the current range,
    // without committing to a stop at any of them.
    while (
      stationIndex < stations.length &&
      stations[stationIndex][0] <= reachablePosition
    ) {
      pushMax(availableFuel, stations[stationIndex][1])
      stationIndex += 1
    }

    // Out of range and out of recorded offers: the target is unreachable.
    if (availableFuel.length === 0) {
      return -1
    }

    // A stop is forced. Retroactively count one at the passed station
    // with the largest offer, extending the range as far as possible.
    reachablePosition += popMax(availableFuel)
    stopCount += 1
  }

  return stopCount
}
```

With the example input, `minimumRefuelStops(100, 10, [[10, 60], [20, 30], [30, 30], [60, 40]])` returns `2`, matching the trace above.

Below are the two heap helpers. They store the values in a plain array arranged so that every parent holds a value at least as large as its children, which keeps the maximum at index 0. Function declarations are hoisted, so defining them after `minimumRefuelStops` works fine.

```ts
function pushMax(heap: number[], value: number): void {
  // Place the new value at the end, then bubble it up
  // past any smaller parent until the order rule holds.
  heap.push(value)
  let index = heap.length - 1

  while (index > 0) {
    const parent = Math.floor((index - 1) / 2)

    // The parent is at least as large, so the value is in place.
    if (heap[parent] >= heap[index]) {
      break
    }

    // Swap the value with its smaller parent and continue upward.
    const parentValue = heap[parent]
    heap[parent] = heap[index]
    heap[index] = parentValue
    index = parent
  }
}

function popMax(heap: number[]): number {
  // The largest value always sits at index 0.
  const maximum = heap[0]

  // Array.pop returns undefined for an empty array, so its type is
  // number | undefined. The main function only calls popMax after
  // checking the heap is non-empty, so the ! tells TypeScript to
  // trust that a number came back.
  const last = heap.pop()!

  if (heap.length === 0) {
    return maximum
  }

  // Move the last value to the top, then sink it down
  // below any larger child until the order rule holds.
  heap[0] = last
  let index = 0

  // No loop condition fits in the header, because the stopping point
  // is discovered mid-body: the loop breaks once the value stops
  // sinking, and it always does, since the heap has finite depth.
  while (true) {
    const left = index * 2 + 1
    const right = left + 1
    let largest = index

    if (left < heap.length && heap[left] > heap[largest]) {
      largest = left
    }

    if (right < heap.length && heap[right] > heap[largest]) {
      largest = right
    }

    // Neither child is larger, so the value has settled.
    if (largest === index) {
      break
    }

    // Swap with the larger child and continue downward.
    const currentValue = heap[index]
    heap[index] = heap[largest]
    heap[largest] = currentValue
    index = largest
  }

  return maximum
}
```

The heap supplies the largest unused fuel amount from stations inside the reachable range. The greedy decision is which reachable station to count as a stop when more range becomes necessary.

## When a greedy rule is unsafe

Coin denominations `[1, 3, 4]` show why a plausible local rule is not enough. Repeatedly choosing the largest coin for amount `6` uses `4 + 1 + 1`, but `3 + 3` uses fewer coins. If this input looks familiar, it should: the dynamic programming lesson used the same coins to motivate comparing every allowed move instead of trusting the best-looking one. Without a proof that the local rule preserves an optimal result, use dynamic programming or another complete search method.

## Common mistakes

These are the errors that show up most often when applying greedy rules:

- Calling an algorithm greedy without stating, in one sentence, what its local choice is.
- Supporting the rule with a few examples where it happens to work, instead of a swap or boundary argument that covers every input.
- Tracking every jump route individually when the farthest boundary already summarizes what all of them can reach.
- Sorting intervals by start time when the goal is to maximize the count, letting one long early meeting block several short ones.
- Treating half-open intervals that share an endpoint as overlapping, which rejects valid back-to-back selections.
- Refueling immediately at every station instead of delaying the decision until a stop is forced.
- Taking the smallest recorded fuel amount at a forced stop, when each stop should add the most reach possible.
- Applying a coin-selection rule that works for one denomination set, like standard currency, to a set where it fails.
