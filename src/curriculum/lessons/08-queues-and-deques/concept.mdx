# Queues and Deques

Picture a shared printer in an office. Print jobs arrive one after another, and the fair thing to do is obvious: whoever submitted first prints first. New jobs join the back of the line, and the printer always takes the job at the front. A structure that works this way, add at the back and remove from the front, is called a queue, and the ordering rule has a name too: first-in, first-out, or FIFO.

Sometimes one end is not enough. A few problems in this lesson need to add and remove at the front *and* the back of the line. That two-ended variant is called a deque, short for double-ended queue and pronounced "deck". A queue is really just a deque where you have promised to use only one end for adding and the other for removing.

JavaScript has no built-in queue or deque class, so in this lesson we build both out of a plain array and one or two plain numbers that mark where the line currently starts and ends. That sounds like a workaround, but it turns out to be both simple and fast, and you will see why in a moment.

## Process work in arrival order

Here is a queue problem shaped like a real scheduler. Each job needs some amount of processing time, but the processor only ever gives a job a fixed slice of time, called a quantum, before moving on. The quantum is a positive number; a zero or negative slice would mean a job could take a turn and make no progress, circling the line forever. Process the front job for one quantum; if it still has time remaining, send it to the back of the line to wait for another turn. Return the order in which jobs received processing.

Take `jobs = [{ id: "a", duration: 5 }, { id: "b", duration: 2 }, { id: "c", duration: 3 }]` with `quantum = 2`. Job `a` runs first and still needs 3 more units, so it rejoins the back. Then `b` runs and finishes exactly. Then `c` runs, needs 1 more, and rejoins. Now the line holds `a` then `c`, and the rounds continue until everyone finishes.

The tempting way to remove the front of an array is `Array.shift()`. It works, but every call to `shift()` moves every remaining element one slot to the left so the array stays packed against index 0. Every processing turn starts with one of those calls, and jobs that rejoin the line create many turns, so with a long queue the simulation pays O(n) reindexing work per turn, and the total grows with turns times queue length. The fix is to stop moving elements at all. Keep a number, here called `head`, that records where the front of the line currently is. Removing the front item is then just `head += 1`, a single step, and the "removed" entries simply get left behind.

The one rule the code must never break is this: every entry from `head` through the end of `queue` is pending work, in exactly the order it should next run. As long as that stays true, reading `queue[head]` always gives the right next job.

```ts
type Job = {
  id: string
  duration: number
}

export function roundRobinOrder(jobs: Job[], quantum: number): string[] {
  // Copy each job, because we are about to change remaining durations
  // and should not mutate the caller's objects.
  const queue = jobs.map((job) => ({ ...job }))
  const order: string[] = []
  let head = 0

  while (head < queue.length) {
    // Take the job at the front of the line, then move the front
    // marker forward. This is the O(1) replacement for shift().
    const job = queue[head]
    head += 1
    order.push(job.id)

    const remaining = job.duration - quantum

    if (remaining > 0) {
      // The job is not finished, so it goes to the back of the line
      // as a fresh entry with only its remaining time.
      queue.push({ id: job.id, duration: remaining })
    }
  }

  return order
}
```

Run it on the example and `roundRobinOrder(jobs, 2)` returns `["a", "b", "c", "a", "c", "a"]`. You can read the whole story in that output: everyone gets a first turn in arrival order, then the unfinished jobs `a` and `c` cycle through again, and `a`, the longest job, takes the final slot.

Notice the trade the `head` index makes. Finished entries stay in the array, so memory is not reclaimed until the function returns. For a simulation like this that is a fine price for turning every removal into a single increment.

## Keep only possible window maxima

The next problem needs the second end of the deque. Given an array and a window size `k`, report the maximum value inside every contiguous window of exactly `k` values. With `nums = [1, 3, -1, -3, 5, 3, 6, 7]` and `k = 3`, the first window is `[1, 3, -1]` with maximum 3, the next is `[3, -1, -3]` with maximum 3 again, and so on until the last window `[3, 6, 7]` with maximum 7. The full answer is `[3, 3, 5, 5, 6, 7]`.

The slow way rescans all `k` values for every window. The fast way keeps a short list of candidates, values that could still become the maximum of some window, and the whole trick is deciding what belongs on that list. Let's derive it rather than memorize it.

First: should the list hold values or their indexes? It has to hold indexes. A window is defined by positions, and a candidate stops mattering the moment its position slides out of the window. If you stored only the value 3, you could not tell whether it came from a position that is still inside the window or one that expired two steps ago. Store the index and you can check expiry with one comparison, while the value is always one lookup away in `nums`.

Second: when the window advances, the index at the front of the list may now sit outside the window, so the front is where candidates expire. That is one reason we need a deque and not a queue.

Third, and this is the heart of it: suppose the value at the back of the list is 1, and the new value arriving is 3, as happens immediately in our example. Could that 1 ever again be the answer for any window? No. Every future window that still contains the 1 also contains the 3, because the 3 arrived later and therefore expires later. The 3 is bigger and lives longer, so the 1 is dominated on both counts. It can be thrown away, from the back, before the new index is added. Applying that rule every time means the values behind the stored indexes always decrease from front to back, which is why this structure is called a monotonic deque, "monotonic" just meaning the values run in one consistent direction. A pleasant side effect: the front of the deque is always the current window's maximum, for free.

One more piece before the code. Rather than a deque class, the implementation uses the array-plus-markers technique from the first section, extended to both ends: a plain array `deque` and two numbers, `front` and `back`. The live entries are the ones at indexes from `front` up to but not including `back`. Writing that range as `[front, back)`, a square bracket for "included" and a round one for "excluded", is standard notation you will meet often. Removing from the front is `front += 1`, removing from the back is `back -= 1`, and the deque is empty exactly when `front` equals `back`.

```ts
export function slidingWindowMaximum(
  nums: number[],
  k: number,
): number[] {
  if (k <= 0 || k > nums.length) {
    return []
  }

  // The deque is a plain array plus two markers. Live entries sit at
  // indexes from front up to, but not including, back. The entries are
  // indexes into nums, and their values decrease from front to back.
  const deque = new Array<number>(nums.length)
  const result: number[] = []
  let front = 0
  let back = 0

  for (let right = 0; right < nums.length; right += 1) {
    if (front < back && deque[front] <= right - k) {
      // The front candidate's position has slid out of the window,
      // so it expires. Advancing front removes it in one step.
      front += 1
    }

    while (front < back && nums[deque[back - 1]] <= nums[right]) {
      // The back candidate is no bigger than the new value and expires
      // sooner, so no future window can ever prefer it. Drop it.
      back -= 1
    }

    deque[back] = right
    back += 1

    if (right >= k - 1) {
      // The first full window ends at index k - 1. From then on, the
      // front of the deque is always the current window's maximum.
      result.push(nums[deque[front]])
    }
  }

  return result
}
```

`slidingWindowMaximum([1, 3, -1, -3, 5, 3, 6, 7], 3)` returns `[3, 3, 5, 5, 6, 7]`, matching the windows we listed by hand.

Now the runtime, because there is a trap here worth disarming. The code has a `while` loop nested inside a `for` loop, and the reflex is to call that O(n squared). Look at what the inner loop actually does, though: every pass through it removes one index from the deque. An index can only be removed if it was added earlier, each index is added exactly once, and a removed index never comes back. So across the *entire run* of the function, the inner loop's total number of passes cannot exceed n, no matter how those passes are distributed among the outer iterations. Adding that to the n outer iterations gives O(n) overall. This style of argument, bounding total work across all iterations instead of worst-case work per iteration, is called amortized analysis, and it is the standard way to reason about monotonic deques and stacks.

## Use prefix sums with a monotonic deque

The final problem looks like a routine sliding-window exercise until you read one word in the prompt: the values may be negative. Return the length of the shortest non-empty contiguous run of values whose sum is at least a positive target.

Why does negativity matter? The usual sliding window grows the right edge until the sum reaches the target, then shrinks from the left while the sum stays at or above it. That logic silently assumes that growing the window can only raise the sum and shrinking can only lower it, which is true when every value is positive. A negative value breaks both assumptions. Watch it happen on `nums = [3, -2, 5]` with `target = 4`. The window grows to cover all three values, sum 6, so the shrink step fires: dropping the 3 leaves `[-2, 5]` with sum 3, below the target, so shrinking stops and the window records length 3 as its best. But the true answer is 1, because `[5]` alone reaches 5. The window walked past that answer and had no reason to come back, since its rules say a shorter window inside a failing one must also fail. With negatives on board, that rule is simply false.

So we need a tool that does not lean on that assumption. The first ingredient is a prefix sum array: `prefix[i]` holds the sum of the first `i` values, with `prefix[0] = 0` for the empty start. For `[3, -2, 5]`, that gives `prefix = [0, 3, 1, 6]`. Its payoff is that any subarray sum becomes a subtraction: the values between prefix positions `left` and `right` sum to `prefix[right] - prefix[left]`. The question "is there a short subarray with sum at least 4" becomes "are there two prefix positions, close together, whose difference is at least 4". The answer of length 1 we found by eye is sitting right there: `prefix[3] - prefix[2] = 6 - 1 = 5`.

The second ingredient is the monotonic deque again, this time holding candidate `left` positions and this time keeping their prefix values *increasing* from front to back. Both ends earn their removal rule from the problem itself. The front rule: while the current prefix minus the front candidate's prefix reaches the target, we have found a valid subarray, so record its length. And here is the part that deserves a beat of thought: that front candidate can then be discarded for good. Any later `right` would pair with it to form a strictly longer subarray, and we already recorded the shortest one it can produce. The back rule mirrors the maximum problem's logic: if the current prefix is less than or equal to some earlier prefix waiting at the back, the earlier one is dominated. A smaller-or-equal prefix that is also more recent gives every future `right` a sum at least as large over a shorter distance, so the older candidate can never win and comes off the back.

```ts
export function shortestSubarrayAtLeastTarget(
  nums: number[],
  target: number,
): number {
  // prefix[i] is the sum of the first i values, so any subarray sum
  // becomes one subtraction: prefix[right] - prefix[left].
  const prefix = new Array<number>(nums.length + 1).fill(0)

  for (let index = 0; index < nums.length; index += 1) {
    prefix[index + 1] = prefix[index] + nums[index]
  }

  // Same array-plus-markers deque as before. It holds candidate left
  // positions, and their prefix values increase from front to back.
  const deque = new Array<number>(prefix.length)
  let front = 0
  let back = 0
  let best = Number.POSITIVE_INFINITY

  for (let right = 0; right < prefix.length; right += 1) {
    while (
      front < back &&
      prefix[right] - prefix[deque[front]] >= target
    ) {
      // The front candidate completes a valid subarray ending here.
      // Record its length, then retire the candidate: any later right
      // would only pair with it to form a longer subarray.
      best = Math.min(best, right - deque[front])
      front += 1
    }

    while (front < back && prefix[deque[back - 1]] >= prefix[right]) {
      // The current prefix is smaller or equal and more recent, so it
      // beats the back candidate for every future right. Drop the back.
      back -= 1
    }

    deque[back] = right
    back += 1
  }

  return best === Number.POSITIVE_INFINITY ? 0 : best
}
```

Trace it on `nums = [2, -1, 2]` with `target = 3`, where `prefix = [0, 2, 1, 3]`. Position 0 joins an empty deque. Position 1, prefix 2: the difference 2 - 0 misses the target, and 2 is larger than the prefix 0 already at the back, so position 1 simply joins behind it. Position 2 is where the back rule earns its keep: its prefix 1 is less than or equal to position 1's prefix 2, so position 1 is dominated and comes off the back, leaving positions 0 and 2. Position 3, prefix 3: now 3 - 0 = 3 meets the target, so we record length 3 - 0 = 3 and retire position 0. The next front candidate, position 2, gives 3 - 1 = 2, short of the target, so the loop ends and the function returns 3. The whole array `[2, -1, 2]` is the shortest qualifying subarray. And the runtime argument is the same amortized one as before: each position enters the deque once and leaves at most once, from one end or the other, so everything runs in O(n).

## Common mistakes

These are the errors that show up most often when people first use queues and deques:

- Calling `shift()` for every queue removal, which reindexes the whole array each time and turns an O(n) traversal into O(n squared) work.
- Storing values in the deque when the algorithm needs indexes, so there is no way to tell when a candidate has expired out of the window.
- Reading the answer at the front of the deque before removing an expired index, which reports a maximum from a position no longer in the window.
- Removing dominated smaller values from the front instead of the back, which breaks the decreasing order the whole structure depends on.
- Keeping an earlier prefix that is greater than or equal to a later one; the later, smaller prefix wins for every future right end, so the older candidate is dead weight.
- Applying the grow-and-shrink sliding-window rule to input that allows negatives, where a shorter window inside a failing one can still succeed.
- Assuming the nested `while` loops make the algorithm O(n squared); the amortized argument above shows each index is removed at most once.
