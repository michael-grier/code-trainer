# Sliding Window

Suppose you have daily sales numbers, say `[2, 1, 5, 1, 3, 2]`, and you want the best three-day stretch. The obvious approach is to sum every group of three: days 0 through 2 give 8, days 1 through 3 give 7, days 2 through 4 give 9, days 3 through 5 give 6. Each sum starts from zero and adds three numbers. That is fine for six days, but for a million days with a thousand-day stretch you would be adding a thousand numbers a million times, almost all of them numbers you already added a moment ago.

Look at two neighboring stretches and you can see the waste. The stretch over days 0 through 2 is `[2, 1, 5]`, and the next one over days 1 through 3 is `[1, 5, 1]`. They share the middle two values. The only difference is that the 2 on the left fell out and a 1 on the right came in. So instead of resumming, take the previous total, subtract the value that left, and add the value that arrived. One subtraction and one addition, no matter how wide the stretch is.

That moving stretch is called a **window**. Picture a frame laid over the array, covering a few consecutive positions. We track its edges with two indexes, `left` and `right`, and the window is everything from `left` through `right`, ends included. Sliding the frame means nudging one edge forward and adjusting our running totals for the single value that entered or the single value that dropped out.

One word of caution before going further. A window always covers a **subarray**: a contiguous run of elements, with no gaps. In `[2, 1, 5, 1]`, the run `[1, 5]` is a subarray, but `[2, 5]` is not, because it skips the 1 sitting between them. Picks that skip elements are called subsequences, and windows cannot represent them; a frame cannot cover index 0 and index 2 while leaving out index 1. If a prompt says "subsequence", the sliding window pattern does not apply, no matter how much the rest of the problem resembles one.

Now the rule that every sliding window solution lives or dies by. Whatever running values you keep, a sum, a set of characters, a count, they must describe exactly what is inside the window right now, nothing more and nothing less. Every time an edge moves, you update those values before doing anything else. Break that habit once, let one stale value linger, and every answer you record afterward is built on a lie about what the window contains.

## Fixed-size windows

The sales question is the simplest kind of window problem, because the prompt hands you the width. Whenever a prompt fixes a size, `k` elements, 3 days, 5 characters, the window never changes shape. It only slides.

Here is the prompt in full: given daily sales numbers and a window size `k`, return the largest total sales across any `k` consecutive days. With `nums = [2, 1, 5, 1, 3, 2]` and `k = 3`, we already found the four window sums by hand: 8, 7, 9, and 6, so the answer is `9`.

The code keeps one running value, `windowSum`. In the language of the rule above, once the first full window exists, `windowSum` must equal the sum of the most recent `k` values, exactly those and no others. Each loop step adds the value entering on the right, and once the window would exceed size `k`, subtracts the value falling out on the left.

```ts
export function maxFixedWindowSum(nums: number[], k: number): number | null {
  // Reject window sizes that cannot form one full window.
  if (k <= 0 || k > nums.length) {
    return null
  }

  // windowSum tracks the current k-sized window once it exists.
  let windowSum = 0
  let best = Number.NEGATIVE_INFINITY

  for (let right = 0; right < nums.length; right += 1) {
    // Grow the window by including the new right value.
    windowSum += nums[right]

    if (right >= k) {
      // Shrink back to size k by removing the value that fell out.
      windowSum -= nums[right - k]
    }

    if (right >= k - 1) {
      // Now the window is exactly size k, so it can update the answer.
      best = Math.max(best, windowSum)
    }
  }

  return best
}
```

`maxFixedWindowSum([2, 1, 5, 1, 3, 2], 3)` returns `9`, matching the hand count. Notice the last `if`: for the first two loop steps the window holds fewer than three values, so it is not yet a real three-day stretch and has no business updating the answer. Waiting until the window is valid before recording anything is a small move here, but it becomes the whole game in the next section.

## Variable-size windows

A fixed-size window only ever asks "which position?" The more interesting problems also ask "how wide?", and then the width has to change as you go. The usual rhythm is that the window grows until it breaks a rule, then shrinks from the left just enough to fix it.

Here is a classic. Given a string, return the length of the longest contiguous substring with no repeated characters. For `input = "abcabcbb"`, the answer is `3`, from `"abc"`. Nothing longer works, because any four consecutive characters of that string repeat something.

The rule the window must obey is "no duplicates inside". To check it cheaply we keep a `Set` named `seen`, and our exactness rule says what it must hold: precisely the characters currently inside `input.slice(left, right + 1)`. Each step, the right edge advances to bring in one new character. If that character is already in `seen`, the window would contain a duplicate, so the left edge walks forward, evicting characters one at a time, until the duplicate's earlier copy has been thrown out. Only then does the new character enter and the window get measured.

The subtle part is that eviction loop, so let's watch it fail. Trace `"abba"` with a broken version that moves `left` only one step instead of looping. The window grows to `"ab"`, then `right` reaches the second `b`. One eviction removes the `a`, so the window becomes `"bb"`, and we happily record a duplicate-filled window of length 2 as if it were clean. Worse, `seen` now holds one `b` while the window holds two, so when the final `a` arrives, the set reports no duplicate, nothing shrinks, and the code records `"bba"` at length 3. Once the set stops describing the window, nothing downstream can be trusted. The `while` loop exists so the left edge keeps walking until the rule actually holds again, not until we have taken one hopeful step.

```ts
export function longestUniqueSubstring(input: string): number {
  // seen represents the characters in the current window.
  const seen = new Set<string>()
  let left = 0
  let best = 0

  for (let right = 0; right < input.length; right += 1) {
    // Try to add the next character on the right.
    const char = input[right]

    while (seen.has(char)) {
      // Move left until adding char would not create a duplicate.
      seen.delete(input[left])
      left += 1
    }

    // The window is valid again, so include char and measure it.
    seen.add(char)
    best = Math.max(best, right - left + 1)
  }

  return best
}
```

`longestUniqueSubstring("abcabcbb")` returns `3`. The order inside the loop matters as much as the loop itself: shrink first, then add, then measure. Measure before shrinking and you count windows that break the rule; forget the `seen.delete` and the set drifts away from the window it is supposed to mirror.

## Grow and shrink for thresholds

The duplicate problem shrank the window to escape a bad state. This last shape flips that around: the window grows until it reaches a good state, and then keeps shrinking while the state stays good, hunting for the smallest window that still qualifies.

The prompt asks: given positive numbers and a positive target, return the length of the shortest contiguous subarray whose sum is at least the target. With `nums = [2, 3, 1, 2, 4, 3]` and `target = 7`, the answer is `2`, from `[4, 3]`.

Read that prompt again and notice the word "positive". It is not decoration; it is what makes the window's movement trustworthy. When every number is positive, growing the window on the right can only raise the sum, and shrinking it on the left can only lower the sum. So the sum moves in one predictable direction per edge. The moment a window's sum reaches the target, we record its length and try dropping the left value. If the sum is still at or above the target, we found a shorter winner and try again. The instant the sum dips below the target, we can stop shrinking with complete confidence, because with positive numbers, removing more values can never bring the sum back up. That confidence is what lets each index enter and leave the window at most once, keeping the whole thing linear.

Trace the example. The window grows through `[2]`, `[2, 3]`, `[2, 3, 1]` with sums 2, 5, 6, all short of 7. Adding the next 2 gives `[2, 3, 1, 2]` with sum 8, so we record length 4 and shrink: dropping the 2 leaves sum 6, below target, stop. Adding 4 gives sum 10, so we record length 4, drop the 3 for sum 7, record length 3, drop the 1 for sum 6, stop. Adding the final 3 gives sum 9, record length 3, drop the 2 for sum 7, record length 2, drop the 4 for sum 3, stop. Best seen: `2`.

```ts
export function minSubarrayLengthAtLeast(
  nums: number[],
  target: number,
): number {
  // sum tracks the current [left, right] window.
  let left = 0
  let sum = 0
  let best = Number.POSITIVE_INFINITY

  for (let right = 0; right < nums.length; right += 1) {
    // Grow the window until it reaches or passes the target.
    sum += nums[right]

    while (sum >= target) {
      // This window reaches the target, so record its length.
      best = Math.min(best, right - left + 1)

      // Then shrink from the left to look for a smaller valid window.
      sum -= nums[left]
      left += 1
    }
  }

  // If no valid window was recorded, report 0.
  return best === Number.POSITIVE_INFINITY ? 0 : best
}
```

`minSubarrayLengthAtLeast([2, 3, 1, 2, 4, 3], 7)` returns `2`.

Now watch the positivity assumption fail. Run the same code on `nums = [1, -4, 7]` with `target = 7`. The sums as the window grows are 1, then -3, then 4, never reaching 7, so the function returns `0`, meaning no valid window. But `[7]` by itself is a valid window of length 1. The negative number broke the one-direction guarantee: dropping the -4 would have raised the sum, so shrinking could have created a valid window the code assumed was impossible. When negatives are allowed, "the sum is too small, so stop shrinking" is simply false, and this pattern gives wrong answers rather than slow ones. Reach for a different tool there, such as prefix sums.

## Common mistakes

These are the failures that show up most often, and each one traces back to a rule this lesson already walked through:

- Updating the answer before the window is valid, like measuring `"bb"` in the duplicate trace, or counting a not-yet-full fixed window.
- Forgetting to remove the departing item from the running value, so the sum or set describes a window that no longer exists.
- Moving `left` a single step when the window may need to shrink several times, which is exactly what broke the `"abba"` trace.
- Applying the grow-and-shrink pattern to input with negative numbers, where shrinking can raise the sum and the stop condition lies, as `[1, -4, 7]` showed.
- Treating a subsequence problem as a sliding window problem. As the introduction explained, a window can only cover a contiguous run.
